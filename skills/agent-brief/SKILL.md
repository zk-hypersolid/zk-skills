# Agent brief

brief 的长度跟着风险走，不跟着清单走。执行方是同级的强模型：给它目标和原始材料，方法它自己会选。你写下的每一句判断都会被它当真，写得越多，带进去的偏差越多。

## 每次都写（通常三到六行）
- 用户原话：整段照抄，或给会话记录、文件的路径。不挑句拼接，不转述。
- 做到什么算完、这次不做什么：只写原话里没有的。
- 材料在哪：路径、链接、ref。指向原文，不写摘要。
- 产出写到哪；消息里只回结论和路径。
- 首段要它写：它理解的意图，以及 brief 和实际对不上的地方。

## 只在需要时加
- **结果依赖文件状态**（审计、复现、改代码）：先列出所有候选（分支、未合并的 PR、tag、部署记录），再钉 40 位 ref，并写一句它的来历（谁指定的、部署记录、PR）。说不出来历，先单独派一步确认对象。写明哪一两条不符就停，不许换成近似的 ref 或文件。
- **独立评审、交叉验证**：不给我的结论、方案和怀疑清单；被审对象的自我声称是待核项；问题本身可以质疑。
- **会写文件，或和别的执行方并行**：写明它的工作区和不许碰的路径。
- **ZK 说过的话**：带日期和当时在说哪件事；评审和探索里是待核项。不写「已定」。

## 不要写
- 我没核实的判断、对材料的摘要、我心里的方案。真要提，写成「待核：…，怎么查」。
- 方法步骤、报告结构、篇幅。核对任务可以给检查清单，但清单要来自执行方自己能读到的文件。

## 发出前问一句
这次如果白跑，最可能是哪条前提错了？它在 brief 里是我核过的，还是我顺手写的？

## 结果跑偏时
先读首段的意图和「对不上的地方」；再核它用的 ref 是不是你要的；最后搜「改用」「fallback」「instead」。
